# SB3 UI — complete functional audit

**Audited:** 2026-07-23 (afternoon), against the live box `http://100.102.3.20:5050` (Neptune, `main`).
**Method:** every `/api/*` string extracted from `ui/sb3.html` (74 distinct), every one probed live with the
method its JS uses; every handler read to confirm what it sends and how it renders the reply.
**Backends during audit:** SDRTrunk 637 / icecast 621 / SDRangel 26379 unchanged; trunk 200, analog 200 throughout;
reconciler left PASSIVE.

> **Why this audit exists.** Previous reports called features "verified end-to-end" after testing only the paths
> that worked. The Favorites wizard was the case in point: Metro Nashville and Middle TN Regional returned
> channels, so it was declared working — while LTR systems and the entire analog path returned nothing. This pass
> tests the paths that fail, not just the ones that succeed.

---

## The two failure modes that shape everything below

Established by reading `fetchJSON` / `postAPI` / `postJSON` in `ui/sb3.html` and confirming against the server:

| Case | Server reply | Client behaviour | User sees |
|---|---|---|---|
| **Unimplemented GET** | **HTTP 200** `{ok:false,"error":"not-implemented-in-3.1"}` | `fetchJSON` only throws on `!r.ok` — 200 **does not throw** | **Panel renders blank/zero. No error. Silent.** |
| **Unimplemented POST** | **HTTP 501** `{ok:false,"error":"not-implemented"}` | `postAPI`/`postJSON` throw on `!r.ok` | Red status message — honest failure |

This is the single most important structural fact in the UI: **anything backed by a GET degrades silently and is
therefore categorised BROKEN, not STUB**, because a blank panel is indistinguishable from "nothing to report".

`sb3/ui/server.py` implements **21** endpoint/method pairs. The UI calls **74** endpoints. The rest fall through
to the two catch-alls above.

## Top 5 issues by real-world impact

1. **~~No audio in the UI at all~~ — FIXED this pass (`8a09804`).** Both players pointed at a `/stream/` proxy SB3
   does not serve → 404 → play did nothing, silently. One missing status field. This is the one that most
   affected daily use, and it had been sitting under "verified" reports.
2. **The Hit Feed is permanently empty and looks like a quiet band.** `/api/hits` always returns `items:[]`
   because SB3 has no hit log. The three last-hit chips read `--` forever. A user cannot tell "no hits" from
   "not implemented".
3. **Digital preflight reports `ready:true` having run zero checks.** A green light that means nothing is worse
   than no light — this is the exact "useful liar" pattern the architecture doc warns about.
4. **Every write outside gain/squelch/filter/tune/volume is a 501.** 24 STUB controls: all 5 service-restart
   buttons, all 6 band-scan presets, avoid, auto-squelch, hold, VLC, dongle power, USB reset, reboot, BT,
   latency, all WX actions, and the wizard's entire save path. The UI presents a fully-featured control surface
   over an SB3 that implements 5 write endpoints.
5. **Unimplemented GETs degrade silently.** 14 BROKEN entries are all this one bug class: HTTP 200 + `{ok:false}`
   sails past `fetchJSON`, and the panel renders empty. Fixing this centrally (see below) would convert a dozen
   silent liars into honest stubs in one change.

## Recommendations, in order

1. **Make unimplemented GETs honest (one change, biggest ratio).** Either return **501** for unknown `GET /api/*`
   so `fetchJSON` throws, or have the render layer check `payload.ok === false` and show "not implemented in SB3".
   Converts ~14 silent failures into visible ones. *Caveat:* returning 501 will surface errors in panels that
   currently look calm — that is the point, but expect the UI to get noisier.
2. **Fix the two liars specifically:** `/api/digital/preflight` should not say `ready:true` with no checks, and
   `/api/hits` should distinguish "no hit log in SB3" from "no hits".
3. **Decide the favorites story.** The wizard now browses real Nashville data but cannot save. Wiring
   `POST /api/scan/state` to a store is easy; deciding what a saved list *does* (drive SDRTrunk? an avoid list?
   nothing?) is yours. I deliberately did not build a store nothing reads.
4. **Hide or mark the dead surface.** 24 STUB + 5 unclickable controls are visible and inviting. Either grey them
   with a "not in SB3" tooltip, or remove them. Right now the UI over-promises badly.
5. **Philly tab:** the Pi answers `/api/status` and `/api/hits` but 404s the profile/pause/resume API because it
   was repurposed to `rtl_tcp`/gqrx. Either restore the scanner service on the Pi or trim the tab to the
   status+stream it can actually serve.

## Explicitly NOT verified

Honesty about coverage, since that is what this audit is for:

- **`<pi>/api/restart` (Philly Restart)** — not fired; it would restart a service on a remote box.
- **Browser click-through of every control** — the in-app browser tool hung repeatedly this session (timed out
  even on a single-line `fetch`). Everything above is proven with `curl` using the exact URL, method and
  parameters the JS sends, plus reading the handler and render path. Where behaviour depends on rendering I say
  so rather than claiming a visual confirmation I did not make.
- **Audio actually being audible** — the stream URL now returns 200 and the player src resolves to it; I did not
  listen to it.
- **Destructive POSTs** (reboot, USB reset, dongle power, profile delete) — verified only that they reach the
  501 catch-all, which has no handler and therefore no side effect. Not exercised against a real implementation.
